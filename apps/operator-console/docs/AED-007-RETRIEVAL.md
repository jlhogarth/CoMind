## Architecture and authorization

The `/aed` client uses the existing Supabase browser client for a Supabase Auth email link and obtains its own session access token. The Next.js server verifies that token with Supabase Auth `getUser(token)` on each request. A valid user UUID must also be present in server-only `OPERATOR_CONSOLE_AED_OPERATOR_IDS`. This is explicit AED authorization, independent of the perimeter. Anonymous, invalid, and unlisted identities are rejected before the database reader is created. A dedicated direct PostgreSQL reader uses fixed, parameterized SELECT queries for `comind_pm.pm_aed_monitor_execution` and `comind_pm.pm_aed_monitor_event`. Browser roles still have no direct table SELECT grant. No arbitrary relation name, SQL, sort expression or write method is accepted.

On November 5 the Data API dashboard showed `comind_pm` was not among the two exposed schemas. The original service-secret Data API adapter cannot work as written. The revised adapter uses a dedicated database reader login and keeps that schema outside the Data API. `db/migrations/20261105_001_aed_007_reader_role.sql` proposes exact SELECT grants and two role-specific RLS policies. It has not been applied. Isolated PostgreSQL validation and C4 approval are required before applying it to the existing project. A password must be provisioned securely outside Git and bound to the Test server as `AED_MONITOR_DATABASE_URL`. The server validates the database role and read-only transaction for every request, with TLS certificate validation.

`OPERATOR_CONSOLE_AED_ACCESS_MODE=enabled` activates the route; disabled or incomplete configuration returns 503. The operator UUID allowlist must be populated with verified Supabase Auth identities, never email guesses. The reader also requires `AED_MONITOR_DATABASE_CA`, the Supabase Root 2021 CA PEM from the project's Database Settings. The connection URL must omit `sslmode` and other query options that could override the Node PostgreSQL client's TLS configuration. The server verifies the CA chain and pooler hostname. The browser bundles only `NEXT_PUBLIC_SUPABASE_URL` and `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`. The server must remain behind the established Console deployment perimeter. Supabase email-link redirect URLs must be configured for the intended Test Console origin. At inspection the Site URL was `http://localhost:3000` and no redirect URLs were listed. Tokens are carried in Authorization headers and are never placed in query strings. Responses use private no-store headers.

## Endpoint contract

| Method and route | Parameters | Response | Bounds |
| --- | --- | --- | --- |
| GET `/api/aed/executions` | `page`, `pageSize` | Execution IDs, lane, first/last event, count, run URL, source and artifact hashes | Last timestamp descending, ID ascending; 1 to 100 rows |
| GET `/api/aed/executions/{id}` | `page`, `pageSize`, optional `kind`, `state` | Execution summary and ordered event fields | Sequence ascending; 1 to 100 rows |

Pages are positive integers at most 10,000, page size at most 100, ID is exactly 24 lowercase hex characters, filters are bounded identifiers. Invalid input returns 400, missing execution 404, missing/invalid identity 401, unlisted identity 403, and unavailable configuration, identity provider or data source 503. Only approved fields are returned. Raw `payload` is withheld. The response includes `payload_sha256`, elapsed time, and the recorded cost value when present. A null cost means unmeasured. No derived status is asserted from the stored events. Run links render only if their host/path matches the CoMind GitHub Actions run pattern.

The current allowlist is a server runtime configuration, not a database authorization ledger. Updating it requires a trusted deployment configuration change. Authentication lookup and server-side reads are bounded but do not yet include an operator access audit record or request rate limit. The dedicated reader is intended to have no access beyond the two monitoring tables.
