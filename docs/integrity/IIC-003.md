# IIC-003 NDT-001 Hard Enforcement

## Purpose

IIC-003 promotes NDT-001 No Dead Path from proven shadow detection to CoMind hard acceptance enforcement for new statically provable dead paths.

NFS-001 remains a shadow review control. Its candidates stay visible but do not block merely because a heuristic matched.

## Evidence basis for promotion

NDT-001 was exercised through two accepted real pull-request cycles before promotion:

1. IIC-001 established the detector, corrected generated-TypeScript false positives, and reached a zero-finding repository scan.
2. IIC-002 refactored the engine without changing the NDT fingerprint contract, then produced a second zero-finding NDT repository scan before and after reconciliation with current `main`.

IIC-002 also proved that NFS candidates can coexist with enforcement semantics without becoming blocking NDT debt.

## Enforcement rule

The Implementation Integrity workflow now runs the engine with `--mode enforce`.

An unbaselined finding classified `verified-risk` causes a nonzero exit. NDT-001 currently emits deterministic `verified-risk` findings. NFS-001 emits `candidate` findings and remains nonblocking.

The accepted repository has zero NDT debt, so IIC-003 does not create a baseline or suppression file.

## Anti-bypass controls

`scripts/check_integrity_enforcement_contract.py` validates that the primary workflow:

- invokes the integrity engine exactly once;
- uses `--mode enforce`;
- does not invoke `--mode shadow`;
- does not use `--baseline`;
- does not use `continue-on-error: true`;
- runs the regression and enforcement-adversarial suites;
- self-validates the enforcement contract;
- retains `contents: read` permissions;
- runs for pull requests and pushes to `main`.

The primary workflow performs this self-check, and the independent `Integrity Governance` workflow performs the contract check and adversarial tests separately.

## Adversarial acceptance cases

The enforcement suite proves that:

- a missing workflow executable path blocks;
- a missing local action blocks;
- a missing package executable path blocks;
- an NFS candidate remains visible but nonblocking;
- a workflow downgrade to shadow mode is rejected;
- adding a baseline argument is rejected;
- making the enforcement step continue on error is rejected.

## Repository-level limitation

At promotion time, GitHub reports `main` branch protection disabled and no required status checks configured. Therefore IIC-003 is a hard CoMind development/acceptance gate and a failing GitHub Actions check, but GitHub itself does not yet provide an independent repository-setting guarantee that a privileged actor cannot merge around the check.

This limitation must remain explicit. Enabling required-status-check branch protection or an equivalent repository ruleset is a separate repository-administration hardening action. IIC-003 does not claim that setting exists.

## Governance boundary

IIC-003 changes repository development controls only. It does not activate Production, modify database state, grant authority, use paid providers, or change feature-lane implementation behavior.

## Recovery

Revert the IIC-003 workflow and governance changes to restore shadow-mode operation. No live-state rollback exists.
