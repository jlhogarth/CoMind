# Live Foundry Stage 1 Budget Authority Deployment Runbook

## Purpose

Issue #116 prepares the first live CoMind Supabase dependency required by the Foundry Agent substrate: the existing FinOps and current-runtime budget-authority chain.

This stage does not activate Agents, Virtual Employees, Foundry orchestration, work leasing, ACP continuity, ChatGPT archive ingestion, or paid provider execution.

The terminal state for Stage 1 is a live, queryable budget-authority substrate with current-runtime provenance binding available and zero persistent Agent execution evidence.

## Evidence-state boundary

This document is a deployment procedure. Its existence is documented intent.

A merged implementation is repository implementation.

A green `Live Foundry Stage 1 Readiness` workflow is isolated verification.

A successful Supabase migration operation is deployment evidence for the specific migration only.

A successful read-only post-deployment verifier is tested deployed-control evidence for the Stage 1 database contract.

None of those states proves an operating Agent, evidence-backed compliance, certification readiness, or certified conformity.

## Authority boundary

Repository inspection, isolated PostgreSQL verification, read-only live Supabase inspection, documentation, and CI may proceed under the Issue #116 T3 engineering lane.

Any live Supabase schema or data mutation in this runbook requires explicit C4 human authorization in the active conversation after exact-head readiness evidence has been reconciled.

Authorization for deployment is not evidence that deployment succeeded.

Authorization for Stage 1 does not authorize Stage 2 Foundry substrate migration `20261008_006`, security migration `20261008_007`, later runtime migrations, credential changes, Agent population, or provider calls.

## Why the raw 2026-09-10 FinOps migration must not be deployed live

`db/migrations/20260910_001_comind_finops_resource_governor.sql` predates the current CoMind v2 runtime identity model.

Its original contract references legacy relations:

- `public.projects`
- `public.agents`
- `public.comind_governance_decisions`

The live CoMind database does not contain those relations. Current identity and execution provenance lives under `comind.cm_*`.

The historical isolated test fixture created those legacy public relations only to test the old migration. That fixture explicitly does not model current production wiring.

Creating compatibility copies of the legacy relations in production would establish competing identity or governance authorities. Stage 1 forbids that approach.

The original migration also seeds a legacy `FinOps and Resource Governor` row into `public.agents` and inserts a legacy governance-decision row. Those seed writes are not permitted in the live CoMind v2 projection.

## Security boundary carried forward

The Stage 1 monetary layer uses `service_role` as a trusted backend role and the current server provider path uses the `comind.cm_*` budget-authority adapter.

The historical FinOps base also contains lower-level service-role callable functions and direct table privileges required by its original `SECURITY INVOKER` function contract. Stage 1 does not grant those capabilities to a Virtual Employee or external actor.

Before any Agent receives database capability authority, the Foundry capability broker and the separate security prerequisite gate must constrain what an Agent can invoke. Do not equate possession of a server-side service credential with Agent authorization.

`20261008_007_foundry_security_prerequisites.sql` remains a separate production security milestone because it changes RLS and role access across the broader `comind` schema. It must not be bundled into Stage 1.

## Failure handling and forward repair

### Failure before any Stage 1 migration commits

Preserve the read-only evidence and correct the repository or deployment plan. No database rollback is needed if no mutation occurred.

### Failure inside a migration operation

Stop immediately.

Do not assume transactional rollback merely because the migration SQL contains transaction boundaries. Read back:

- migration history;
- affected relations;
- affected columns and constraints;
- functions;
- indexes;
- triggers;
- RLS state;
- grants;
- relevant row counts.

If the failed migration did not commit, correct the repository issue and rerun only after exact state is proven.

### Failure after a migration commits

Do not drop live objects merely to recreate the pre-deployment shape.

Prefer a reviewed additive or corrective migration that advances from the proven committed state.

Any destructive rollback requires a separate explicit human authorization with evidence that destructive rollback is safer than forward repair.

Do not apply later Stage 1 migrations to compensate for an unknown earlier state.

### Unexpected persistent data

If Agent rows, Agent runs, PM Agent runs, unexpected provider rows, or unrelated application-row changes appear, stop the deployment and preserve them as evidence until the cause is proven.

Do not delete evidence merely to make the deployment appear clean.

### Security regression

If Stage 1 introduces an unexpected privilege, RLS, function exposure, or Security Advisor regression, stop progression to Foundry Stage 2. Repair and independently verify the security delta before continuation.

## Roll-forward terminal condition

Stage 1 is accepted only when all of the following are true from independent evidence:

- exact accepted repository state identified;
