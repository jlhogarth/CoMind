# AGCOL-002 bounded parallel collaboration and MCP Test slice

Issue #553 continues the merged sequential AGCOL-001 pilot. This slice is T2 because specialist handoffs create cross-agent state and governed Foundry executions. It is isolated Test code, not a Production activation or an enterprise certification claim.

## Execution contract

`runParallelCollaboration` takes an acyclic graph of 2–32 tasks, at most eight in flight, with distinct profile and task identities. Independent roots may start concurrently. A dependent task receives canonical predecessor receipts in declared order only after every predecessor returns successful terminal execution and matching evidence. Before claiming work, the host persists an input-redacted graph manifest. A restart loads completed receipts only after checking the existing lease, authority, execution and evidence records. An incomplete or mismatched recovery blocks before a new claim. Each task acquires a task-matched fenced claim and renews it during long execution. The host finishes or releases the exact token and epoch, but the token is never returned in a public receipt or progress event. The accountable `authorize` callback supplies an exact task-specific decision after the join; the coordinator never fabricates or shares decisions. Foundry independently checks the profile, capability, scoped grant, request/decision binding, environment, budget and idempotency. Failed work blocks new scheduling; already running work drains to a terminal result. A human stop blocks new claims and prevents a late success from completing after the stop. The returned receipts are ordered by the submitted graph, not completion timing.

An adapter through `createReadOnlyMcpAdapter` is restricted to C1, `read`, `evidence_resource`, a bounded target reference and synthetic input. A local MCP process performs `initialize`, `tools/list`, and `tools/call` over JSON-RPC stdio with an exact single-tool allowlist. The fixture reads only deterministic synthetic evidence, uses no network or credentials, and returns a strictly validated four-field resource record. No arbitrary tool text is passed as an instruction. Receipt persistence is supplied by the host before Foundry reports a successful adapter result. It captures operation/context identity, request/result fingerprints, resource, source, elapsed time and zero fixture cost.

## Boundaries and recovery

These modules do not register themselves as a persistent worker service or mint grants. The application must bind an allowlisted capability to the adapter, supply an independent authorization authority and a durable receipt writer. The fixture MCP server is deliberately confined to Test. The exact task/project claimant is versioned in `20261110_001_agcol_002_exact_task_claim.sql` and checked twice with a rollback-only verifier. The guarded live Test harness registers synthetic specialists, a non-cost-bearing capability, exact target grants and task-bound decisions, then uses the existing Foundry lease and finish functions. It stores a manifest, phase observations and MCP receipts in the canonical evidence table, revokes run grants and reads back tasks, leases, outcomes and evidence. The live workflow runs only for the exact same-repository branch and owner actor. Claim and finish callbacks reject mismatched tasks, stale tokens and epochs. The graph's in-process memory is not a durable queue. A host can restart from its manifest and verified terminal receipts; partial executions without terminal evidence remain blocked for reconciliation. No persistent host, scheduler, AED binding, Console projection, broad MCP source trust or Production activation is implied. The existing Test proof is recorded in `docs/provenance/2026-11-10-agcol-002-test-acceptance.md`; the new service-readiness changes require a fresh exact-head live proof. Reviewer dissent and per-provider resource charge accounting remain open. Do not describe this as enterprise certification.

## Traceability

- Authority: GOV-001 T2 and Foundry C1 isolated checks, separate human authority for Production.
- Identities/resources: distinct specialist Foundry profiles, task IDs, plan/resource target, fixture MCP tool.
- Controls: grant and authorization checks in Foundry; bounded concurrency and evidence join here; strict MCP input/output allowlist; no credentials in model input.
- Failure: failed specialist blocks dependent scheduling, in-flight operations drain, the result exposes a bounded blocker code and reconciliation flag, and the host reconciles any persisted orphan or revoked grant. Observation failure and lost renewal fail closed.
- Validation: exact-head AGCOL-002 workflow builds server and runs graph, protocol and AGCOL-001 regression tests. Live Test evidence and independent readback must be attached before closing #553.
- Latency/cost: each completed specialist receipt records elapsed milliseconds; MCP fixture receipt records elapsed milliseconds and zero direct tool cost. Host and model overhead remain unknown, never inferred as zero.
