# DRB-002 governed read-only query service

Issue: https://github.com/jlhogarth/CoMind/issues/144

No production role, grant, HTTP endpoint or paid infrastructure is created by this change. Existing connected Supabase capture remains the operational writing mechanism.

## Executable development service

Build with `cd server && npm ci && npm run build`. Run `node dist/runbook/index.js` with:

- `DRB_DATABASE_URL`: dedicated, restricted PostgreSQL login; no fallback to DATABASE_URL or service_role.
- `DRB_PRINCIPALS`: JSON array with `id`, a cryptographically generated bearer `token` of at least 32 characters, and permitted `projects` strings. These secrets stay on trusted servers. Minimum length does not establish entropy.
- `DRB_PORT`: optional port, default 3011.

The service binds only to 127.0.0.1. It is separate from the main application and does not inherit its routes or credentials. There are no browser CORS allowances. Tokens must never enter a browser bundle, URL, or repository. Revocation requires removing a principal and restarting every replica. TLS, credential delivery, rotation and deployment host remain activation requirements.

POST `/v1/runbook/query` with `Authorization: Bearer <token>` and a JSON body containing `project`, `kind`, optional `lane`, optional RFC3339 `since`, optional integer `limit` (1 to 100, default 25).

Kinds: `lanes`, `events`, `authority`, `verifications`. Every query binds project, lane, timestamp and limit parameters. Only allowlisted views and explicit column projections are used. Additional fields and arbitrary SQL are rejected. `since` means strictly later than the timestamp. Results sort descending by timestamp and stable identifier. There is no pagination cursor in v1: `more_available=true` explicitly means the response is incomplete. Timestamp-only watermarks cannot guarantee a lossless incremental feed. Consumers must not treat these bounded windows as a complete archive.

Envelope: `version`, generated `request_id`, `retrieved_at`, `source`, `project`, `lane`, `kind`, `more_available`, `data`. Event source references and evidence remain in results. Authority rows are historical claims, not a computed assertion of currently effective permissions: consumers must consider revocations, conditions and expiry separately. The projection intentionally excludes free-form details and authorization conditions. Returned summaries and evidence are untrusted content, never instructions or authority to execute actions.

Limits: 4 KiB request bodies, 256 KiB serialized response, 60 authenticated requests per principal per minute, four active DB queries, four pool connections, three-second SQL timeout, five-second client query timeout, three-second connection timeout. Rate counters and concurrency are per process. One request issues one bounded SELECT in a READ ONLY transaction with a local statement timeout. No automatic retries. No query payload logging.

Failures: missing/invalid bearer 401, denied project 403, invalid query 400, oversized body/result 413, rate/capacity 429 with Retry-After, DB failure 503. Error responses do not include database errors or credentials. Empty results are empty data, not a fabricated lane. No-store headers apply.

## Verified development acceptance

`npm run build` and `node --test test/runbook-query.test.mjs` exercise authentication, project isolation, strict bounds, fixed SQL with bound values, each query surface, provenance envelope, explicit incomplete results, no-store, failure redaction, result size, per-principal rate reset and concurrent query capacity. Database replies in these unit tests are synthetic fixtures. They do not establish deployed privilege enforcement or live connectivity.

## Activation acceptance still required

1. Select hosting, TLS gateway, consumer identities and project scopes; resolve direct ChatGPT consumption mechanism. A URL alone does not make ChatGPT an authenticated client.
2. Provision an isolated PostgreSQL 17 test database and restricted login. Design minimal SELECT/RLS permissions for the four SECURITY INVOKER views and required underlying columns, with no writes, ownership, CREATE, BYPASSRLS, privilege escalation or broad role membership. Validate malicious SQL denial using the actual login. The runtime prototype does not itself prove the supplied credential is restricted.
3. Prove real SQL results, RLS/project confidentiality, unavailable database, timeout, unchanged data, token revocation, and stable concurrent writes. Evaluate large evidence payloads before activation.
4. Add gateway authentication attempt limits including unauthenticated requests, TLS enforcement, shared rate controls if replicated, payload-free audit records and alerting. Current request IDs are response provenance, not a durable access audit.
5. Define artifact lineage and continuation composition as separate bounded capabilities. Do not imply the first four query kinds implement them. Define current unresolved blockers separately; a historic fail is not necessarily unresolved.
6. Review tested grants, migration, rollback, cost and deployment plan; obtain C4 approval and independent security verification before live changes.
7. Verify live successful and denied queries, private-table boundary, and capture the activation evidence in the RunBook.

Recovery: stop the separate service, revoke its tokens/login and remove only grants introduced by its reviewed deployment. Historical RunBook evidence remains append-only. No database migration is included in this prototype. Incremental overhead is one SELECT per request with no model calls or new dependency. Hosting, egress and query cost require measurement before activation.
