# IIC-002 Multi-Control Integrity Engine and No False Success

## Purpose

IIC-002 evolves the IIC-001 repository checker into a reusable multi-control integrity engine and adds NFS-001 No False Success as a non-blocking shadow detector.

The governing invariant remains: CoMind's observable representation must not materially exceed verified implementation reality.

## Governance and scope

This increment is T1 reversible repository development under the canonical CoMind Development Environment Contract.

Included:

- the shared implementation-integrity engine;
- its synthetic regression tests;
- the Implementation Integrity GitHub Actions workflow;
- IIC documentation and provenance.

Excluded:

- Production activation or deployment;
- database schema, RLS, grants, credentials, or live data mutation;
- paid-provider execution;
- feature-lane implementation changes;
- automatic baseline or suppression generation;
- NDT-001 or NFS-001 hard-gate promotion.

## Finding model

Every finding now carries:

- `control_id`;
- detector name;
- severity;
- classification;
- repository path and source line;
- target;
- message;
- bounded evidence text;
- stable fingerprint.

The NDT-001 fingerprint contract remains `control_id | detector | path | target` and deliberately excludes source line. Existing NDT evidence identity therefore survives the multi-control refactor.

## Classification semantics

### verified-risk

A deterministic integrity condition that the detector can prove from static repository evidence. NDT-001 uses this classification.

In future enforcement mode, an unbaselined `verified-risk` is blocking.

### candidate

A mechanically observed pattern that may conceal failure but requires contextual review before it can be called a violation. NFS-001 begins with this classification only.

Candidates never block merely because they were detected.

### accepted-pattern and verified-risk promotion

These are review outcomes, not scanner guesses. IIC-002 does not automatically create either classification for NFS-001.

## NFS-001 initial detector scope

NFS-001 reports review candidates for literal patterns including:

1. GitHub Actions `continue-on-error: true`;
2. shell `|| true`;
3. shell `|| :`;
4. shell `set +e`;
5. equivalent literal package-script masking.

The detector preserves the surrounding step or script identity and evidence text in each record.

The following are not treated as failure masking by themselves:

- `continue-on-error: false`;
- `if: always()` cleanup;
- ordinary teardown commands;
- dynamic or ambiguous constructs that cannot be classified safely.

## Enforcement semantics

The engine supports both `shadow` and `enforce` modes.

- Shadow mode reports all findings and exits successfully unless the engine itself fails.
- Enforce mode blocks only unbaselined findings classified as `verified-risk`.
- NFS-001 `candidate` findings remain non-blocking until reviewed evidence supports a stronger classification.

The GitHub workflow remains in shadow mode in IIC-002. This intentionally provides a second real-world exercise of NDT-001 before its separate hard-gate promotion.

## Workflow efficiency

The IIC workflow now uses per-PR or per-ref concurrency cancellation. Superseded integrity runs for the same PR/ref can be cancelled without changing unrelated repository workflows.

## Acceptance evidence required

Before merge:

- all synthetic tests pass;
- NDT-001 fingerprints remain stable;
- the real repository NDT result is reviewed;
- all real NFS candidates are preserved and classified rather than suppressed;
- exact-head Implementation Integrity, No Placeholder, and broad CI pass;
- final collision and freshness checks show no neighboring-lane modification.

## Recovery

Revert IIC-002. No live-state rollback is required.
