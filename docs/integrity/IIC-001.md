# IIC-001 Hard Implementation Integrity Controls

## Purpose

IIC-001 establishes a reusable implementation-integrity control plane for CoMind. Its governing invariant is that the system's observable representation must not materially exceed verified implementation reality.

This lane follows the canonical CoMind Development Environment Contract and `AGENTS.md`. The first slice is repository-only, additive, reversible, and classified T1. It does not change Production, database schema, RLS, grants, credentials, live data, paid-provider access, Foundry, MDO, Conversation History, Operator Console, RuleBook, or VE lifecycle implementation code.

## Enforcement lifecycle

Controls progress through explicit states:

`detect -> classify -> report -> baseline -> prove detector -> enforce`

The current NDT-001 state is **report**. Findings are visible but non-blocking. Engine execution errors remain blocking because a broken integrity checker must not silently report a clean result.

The later enforcement rule is **no new integrity debt**. Existing reviewed findings may be represented by stable fingerprints in a reviewed baseline. New findings are rejected once the control reaches enforcement. Baselines are evidence, not suppressions, and must never be regenerated automatically to make a failing change appear clean.

## NDT-001 detector contract

NDT-001 currently reports only statically provable dead paths:

1. literal repository-local `uses: ./...` references in GitHub Actions that do not resolve to a file or local action directory;
2. literal repository-relative executable operands in GitHub Actions `run` commands when command resolution is unambiguous;
3. literal executable operands in `package.json` scripts, resolved relative to that package.

Dynamic paths are skipped. Workflows containing `working-directory` are skipped for run-command path analysis in this first detector version because resolution context is not inferred. Local `uses` checks remain valid in those workflows.

The detector uses only the Python standard library. Finding fingerprints deliberately exclude line number so harmless line movement does not create artificial new debt.

## Exceptions and exclusions

An integrity exclusion must identify the control, exact scope, rationale, approving authority, evidence, and expiration or reconsideration trigger. It must not hide a regression or disable the evidence that revealed a violation.

IIC-001 has no authorized detector exceptions. Conservative abstention for ambiguous paths is detector behavior, not an exception and not a pass claim.

## Development evidence

Initial local implementation exposed a parser defect: GitHub Actions list-form entries such as `- run:` and `- uses:` were not recognized by the first matcher. The synthetic tests failed. The matcher was corrected to support list-form entries, and the full nine-test suite then passed. This failure is retained because it materially improved detector correctness.

Acceptance requires exact-head GitHub evidence in addition to local tests. Shadow findings from the real repository will be reviewed before any baseline or blocking enforcement is adopted.

## Recovery

The slice is additive. Recovery is repository revert or branch abandonment. No live-state rollback is required.

## Cost and latency

No paid provider, external package, or runtime service is introduced. Cost is limited to GitHub Actions runner time. Repository scanning is bounded by workflow files and non-excluded `package.json` files.
