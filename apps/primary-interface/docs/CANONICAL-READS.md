## Envelope and bounded retrieval

Input requires state (ok/partial/missing/failed/forbidden), observedAt with explicit timezone, reviewed scope, limit 1..100, moreAvailable and rows. Output retains those assertions and reports bounded-window coverage, returned count and unknown total. Successful empty differs from unavailable. Unavailable states cannot carry rows. Partial and moreAvailable remain explicit; neither a full page nor moreAvailable=false establishes complete registry coverage. A source unavailable during refresh must not be replaced by cached success without separate provenance.

The pure projection accepts caller assertions; it does not verify project access, observation clock or SQL isolation. The isolated server path enforces project scope, deterministic ordering, limit+1 retrieval, response byte limits and timeouts. RunBook events use a descending keyset cursor over the exact tuple `(occurred_at,event_id)`: the timestamp is serialized from PostgreSQL with six fractional digits in UTC, and the UUID resolves equal-timestamp boundaries. The first page has no cursor; an overflow response supplies `next_cursor` from its final returned row. The next request must provide both cursor fields, and SQL applies the tuple comparison after project/lane scope. Timestamp-only `since` is rejected for events. Each page rechecks the operator session and project scope. This is bounded keyset navigation, not a snapshot, complete archive, or lossless feed; `more_available=false` describes only that query window. The separate Foundry path enforces operator-session UUID scope and uses its own restricted PostgreSQL login and pool, fixed source query, read-only transaction, timeout, row bound and test RLS policy. The opt-in connected page renders source domains separately. The default cockpit remains disconnected.

## RunBook event tuple pagination

`POST /v1/runbook/query` accepts `cursor_occurred_at` and `cursor_event_id` together only for `kind=events`. The read orders by `occurred_at DESC, event_id DESC`, fetches `limit + 1`, and applies the strict lexicographic predicate `(occurred_at,event_id) < (cursor_occurred_at,cursor_event_id)` for the next older page. The timestamp projection uses UTC text with six fractional digits because converting PostgreSQL `timestamptz` to JavaScript `Date` would lose sub-millisecond precision and could omit rows. The PI event gateway validates cursor pairing, event ordering, returned cursor lineage and that each later page advances beyond its submitted cursor. The browser exposes bounded page size, older-page navigation and browser Back to the prior page. A denied, malformed or unavailable response clears the current page and reports its explicit state.

The disposable PostgreSQL and Chromium acceptance creates synthetic events through the existing append-only capture function, forces overflow with a two-row page, checks UUID tie ordering and cursor continuity, confirms another project's event rows are excluded, and navigates forward/back in the actual reader page. A later synthetic event is appended after page one is observed and before its cursor is followed. The older-page request stays tied to that cursor, while a refreshed first page observes the new event. The browser labels each request as an independent observation of a changing source. Event pages remain bounded and non-lossless. PM decisions, Foundry authorization requests and PI human-action assessments are unchanged and remain separate.
