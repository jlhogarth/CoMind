## Native Foundry request read, isolated extension

`GET /api/pi/foundry-requests?project_id=<uuid>&limit=1..100` is a separate PI path. The operator session carries an explicit optional `foundryProjectIds` allowlist; the handler checks exact UUID scope before accessing the source. It does not call the PM/DRB endpoint, read PM project keys, or infer a project crosswalk. The server uses the separately configured `PI_FOUNDRY_DATABASE_URL`, whose startup preflight requires the `comind_foundry_query_login` identity, a non-owner RLS-enabled source table, SELECT-only access to that relation, no role memberships, no write/DDL privileges and no security-definer function access. A fixed query selects reviewed fields from `comind.cm_foundry_authorization_request` under a read-only transaction. Requested authority, status, reason and evidence references remain source values, not an assessment or execution claim.

`db/test/pi_foundry_reader.sql` is a disposable PostgreSQL fixture only. It grants SELECT on the request table and creates an RLS policy for a fixed synthetic UUID; it is not a deployment migration or production policy. `server/test/pi-foundry-reader.integration.test.mjs` proves the restricted login, denied writes/other relations, row isolation, bounded PI response and operator UUID denial when run after the Foundry substrate fixture. `reader.html` displays the source as text, separately from PM decisions and lanes. A live role/policy, operator UUID assignments, evidence verification rules, revision semantics, and Foundry-to-PM crosswalk remain unresolved.
